# Как работает пайплайн — объяснение для защиты

## 1. Что входит

`analyze.py` читает **сырые байты `.eml`**. Стандартная библиотека `email` извлекает закодированную MIME-тему и `text/plain`, а если его нет, переводит `text/html` в обычный текст. Скрипты, стили и файловые вложения не включаются в текст. SMTP-атрибуты не используются для определения ИИ. Письмо делится на **ровно 4 ключа**: `subject`, `greeting`, `body`, `signature`. Если зоны нет, она пустая, а не нулевая.

## 2. Три независимых признака для каждой зоны

**TF-IDF:** из обучающего набора векторизатор получает частоты слов и пар слов с IDF-весами. Логистическая регрессия вычисляет `tf_score = predict_proba(text)[1]`. Это именно машинное обучение, а не ручной подсчёт ключевых слов.

**Embeddings API:** у `/embeddings` запрашивается числовой вектор текста. Он нормализуется до длины 1. На обучении по каждой из 4 зон усредняются векторы класса AI и HUMAN, получаются два центроида. Для входного текста считается разница косинусных сходств `Δ = cos(text, centroid_AI) - cos(text, centroid_HUMAN)`; `embed_score = sigmoid(8Δ)`. Это **относительный скор**, не доказанная вероятность. Если реальный API эмбеддингов недоступен, `embed_score=None`, и никакой подмены на хэш-эмбеддинг нет.

**Semantic LLM:** POST `/chat/completions` в указанную в `.env` модель. Ей отправляются тип сегмента и текст с инструкцией прислать JSON-массив вида `[{'i':0,'score':0.6}, ...]` (на деле валидный JSON в двойных кавычках). Код требует полный список индексов и числа между 0 и 1; ошибочные ответы отбрасываются. Поскольку генеративные модели не умеют достоверно определять авторство ИИ, этот ответ используется лишь как **один дополнительный признак**.

Получаем `no_llm_score = mean(tf_score, embed_score)` и `with_llm_score = mean(tf_score, embed_score, semantic_score)` по присутствующим значениям. Если пусто приветствие, оно не участвует в среднем.

## 3. Классификатор — Decision Tree

Дерево решений получает **10 признаков**: четыре `no_llm_score`, четыре флага присутствия сегментов, средний `no_llm_score` по непустым зонам и средний `tf_score` по непустым зонам. `DecisionTreeClassifier(max_depth=3)` обучается на **отдельной от TF-IDF** части писем. Дерево даёт `p_tree`, а его правила выводятся в консоль при обучении.

## 4. Отдельные пороги для 4 зон

Для зоны и режима (`no_llm` или `with_llm`) на *калибровочной* выборке сравниваем оценки с известными метками. Перебираются все реальные границы между отсортированными значениями скора, вычисляется:

`Youden J = TPR - FPR`, где `TPR=TP/(TP+FN)` и `FPR=FP/(FP+TN)`.

Выбирается порог с максимальным J; если лучших несколько — их медиана. Пороги сохраняются в `model/thresholds.json`. Если в размеченных письмах нет определённой зоны (например, нет `subject`), вычислить обоснованный порог невозможно, поэтому записывается `null`, а метка зоны будет `UNDETERMINED`. Это честнее, чем выдумывать `0.5`.

**Ограничение:** обучающие данные в примере помечают письмо целиком, а не каждую зону отдельно. Метку письма используем как приближение для зоны, что плохо подходит для писем с человеком и ИИ одновременно. Чтобы научиться определять гибридные письма точнее, нужны собственные `is_ai_subject / is_ai_greeting / is_ai_body / is_ai_signature` в данных и отдельные метки для каждой зоны — текущий код их пока не принимает.

## 5. Decision Engine с порогами

`final_score = 0.5 * средний_скор_непустых_зон + 0.5 * p_tree`.

На калибровочных письмах считаются 90-й перцентиль у людей и 10-й перцентиль у ИИ. Если между ними есть разделяющий зазор, вокруг оптимальной границы Youden формируется узкая зона неопределённости шириной 15% зазора с каждой стороны (не выходя за квантили). При перекрытии распределений используется небольшая зона неопределённости вокруг границы по Youden. Вычисленные `human_cut` и `ai_cut` — независимые от порогов отдельных зон. Правила:

- `final_score < human_cut` => `HUMAN`;
- `human_cut <= final_score < ai_cut` => `UNCERTAIN` (ручная проверка);
- `final_score >= ai_cut` => `AI`.

Если одновременно обнаружены зоны с метками `AI` и `HUMAN`, конечный вердикт принудительно `UNCERTAIN`: это может быть смешанное авторство. Если полное semantic API недоступно, берём отдельно калиброванный `no_llm` режим. Если модель обучалась на API-эмбеддингах, но они не пришли при анализе, вердикт принудительно `UNCERTAIN`: изменился состав признаков и прежние пороги могли стать недостоверными.

## 6. Зачем четыре разных набора данных

* `base`: обучаем TF-IDF и центроиды, не смотрим на test.
* `stack`: обучаем Decision Tree по ответам уже обученных базовых моделей.
* `calib`: вычисляем пороги зон и финальные границы.
* `test`: один раз проверяем на ранее невиденных письмах, сохраняем `ROC AUC`, сбалансированную accuracy, precision, recall и долю `UNCERTAIN` в `test_metrics.json`.

Это уменьшает прямую утечку данных, когда модель обучена и оценена на одних объектах. Но похожие по шаблону синтетические примеры могут оказаться по разные стороны разбиения, и метрики всё равно будут сильно завышены. Нужен **отдельный реальный тестовый датасет**, разнесённый по авторам, моделям и источникам.

## 7. За счёт чего ускорено

* TF-IDF для группы сегментов вычисляется одним `vectorizer.transform`, а не отдельным sklearn вызовом на каждую зону.
* **Один пакет эмбеддингов** и **один семантический пакет** на письмо вместо восьми одиночных запросов; эти запросы выполняются параллельно.
* Большой датасет TF-IDF читает локально, а LLM не используется на `base` и `stack`. API-калибровка ограничена отдельными подвыборками.
* Один HTTP `AsyncClient` повторно использует соединения в рамках серии запросов; конкурентность ограничена. При сбое батча код делит его на части, но **не удерживает семафор**, поэтому нет deadlock.
* SQLite-кэш ключует результат хэшом + настройками модели. Повторный анализ идентичного текста не вызывает платный API заново. Если модель обучена полностью офлайн и не имеет `with_llm` порогов, анализ не отправляет ненужные семантические запросы, даже когда позже введён API-ключ. Ошибки API не сохраняются в кэш.
* FastAPI запускает вычислительную синхронную функцию в threadpool, не блокируя основной event loop.

## 8. Что показывать преподавателю

```sh
python train.py --csv data/demo_synthetic.csv --offline
python analyze.py examples/human_invoice.eml
python analyze.py examples/ai_slop_newsletter.eml
python analyze.py examples/mixed_human_plus_ai.eml --json
uvicorn server:app --port 8000
pytest -q
```

Далее показать `model/thresholds.json`, `model/test_metrics.json`, вывод дерева из `train.py`, и в коде `api.py` запросы `/chat/completions` и `/embeddings`. Обязательно объяснить, что без настоящего API-ключа **только офлайн-тест и мок-интеграция** проверены, и на синтетических шаблонах точность не означает реальную точность определения авторства.
